我按仓库当前 `main` 的代码做的是**静态代码质检 + 优化点定位**，没有在这里重新跑 Vivado 综合/实现，所以最终结论里凡是涉及 WNS/TNS 的部分，都建议你用本地 Vivado 复跑确认。整体看，这个工程已经从“单个实验代码”变成了一个比较完整的 **Nexys A7-100T 多游戏控制台工程**：顶层统一 VGA、菜单、PS/2、LED、七段数码管、蜂鸣器，并通过 4 个 slot 接入不同游戏；工程文档里也明确了 slot API、100MHz 时钟、active-high reset、`pixel_tick`、`display_active`、七段数码管低有效、`buzzer=1` 静音等约定。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/README.md))

## 本轮执行状态

针对本文提到的两个结构风险，本轮已经完成代码调整：

1. slot1/tank 不再保留内部 VGA/PS2 接收链路，改为复用集合机统一 `pixel_x/pixel_y/display_active/pixel_tick` 和 `ps2_byte_ready/ps2_byte_data`。
2. renderer 风险已做全项目清扫：当前 `src/` 下 Verilog 未发现真实 `/`、`%` 运算残留；slot2/slot3/slot4/tank 的 RGB 输出在槽位边界按 `pixel_tick` 寄存；slot3 HUD 弹药十位/个位移出像素组合路径，改为顶层预计算后交给 renderer。

我的严格结论是：**最后一轮优化不建议再大幅加功能，而应该围绕“可综合稳定、时序裕量、资源结构、输入链路一致性、文档与脚本可信度”做收口。** 你现在最值得优先处理的不是某个小的 LUT 百分比，而是几个可能影响验收稳定性的硬伤和时序隐患。

## 一、最优先修的 P0 问题：`slot2` 顶层有重复端口连接

`src/games/slot2/game_slot2_top.v` 里实例化 `slot2_input u_input` 时，`.ps2_clk(ps2_clk)` 和 `.ps2_data(ps2_data)` 出现了两次。这个属于非常明确的代码质量问题：轻则 Vivado 报 duplicate named port / 编译警告，重则影响你最终交付时老师或助教看代码的第一印象。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/src/games/slot2/game_slot2_top.v))

你应该立刻把重复的两行删掉，只保留一次：

```verilog
slot2_input u_input (
    .clk(clk),
    .reset(reset),
    .selected(selected),
    .ps2_clk(ps2_clk),
    .ps2_data(ps2_data),
    .btn_l(btn_l),
    .btn_r(btn_r),
    .btn_u(btn_u),
    .btn_d(btn_d),
    .btn_c(btn_c),
    ...
);
```

这个问题不是“优化建议”，而是**必须修**。最后一轮提交前建议至少跑一次 `synth_design`，保证没有这类基础语法/绑定问题。

## 二、当前时序虽然过了，但裕量太薄，不能把它当成“已经稳了”

仓库里的优化日志显示，项目经历过很严重的时序问题，例如 slot2 曾经出现过约 `-23.994 ns` 的 WNS，后续通过重构和 timing exception 把当前结果推进到了 WNS 正数；最新记录里 WNS 已经到 `0.076 ns`、TNS 为 `0`，bitstream 可以生成。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/docs/优化日志.md))

但是 `0.076 ns` 只有 76 ps，严格说这叫**刚刚踩线通过**，不叫“时序很稳”。最后一轮你做任何小改动，例如改一点显示逻辑、加一点状态判断、调整 case 顺序，都可能让实现结果波动回负数。所以验收前我建议你把目标定成：

```text
最低要求：WNS >= 0，TNS = 0
更稳目标：WNS >= 0.2 ns
理想目标：WNS >= 0.5 ns
```

你现在应该重点看的是**关键路径是否仍集中在 slot2/slot3/渲染/状态逻辑**，而不是只看总资源占用百分比。

## 三、timing exception 已经用了，必须严格审计，不能“用约束掩盖问题”

你的 `scripts/apply_timing_exceptions.tcl` 里对 slot3 RGB、tank VGA、console RGB sample、slot4 state 等路径施加了多周期约束；脚本会打印匹配对象数量，并在对象为空时 warning，这一点是好的。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/scripts/apply_timing_exceptions.tcl)) 同时 `report_timing_post_route.tcl` 也会在实现后重新 source timing exceptions，并生成 timing summary、worst timing、hierarchical utilization、design analysis 等报告。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/scripts/report_timing_post_route.tcl))

但严格质检下这里有一个风险：**多周期约束必须只加在真正由 clock enable 限速的路径上**。比如 VGA RGB 采样如果确实只在 `console_pixel_tick` 时更新，那么按 25MHz 使能理解是合理的；但如果某些状态寄存器、渲染组合逻辑、slot4 state-to-state 路径实际上每个 100MHz 周期都可能变化，那么多周期约束就可能把真实单周期问题隐藏掉。

验收前建议你做三件事：

```tcl
report_timing_summary -report_unconstrained -check_timing_verbose
report_exceptions -all
report_timing -max_paths 50 -sort_by group
```

并保留报告截图。你向老师讲的时候可以说：
“我们没有盲目追求 WNS 正数，而是把 VGA 像素使能类路径与真实 100MHz 状态路径区分开，对多周期路径进行了对象匹配和 unconstrained path 检查。”

这会比单纯说“我 WNS 是正的”更像产品级验收。

## 四、最大的结构性优化点：PS/2 接收链路重复，应统一到顶层

现在顶层 `game_console_top.v` 已经有统一的 `console_ps2_rx`，并把 `ps2_scan_code`、`ps2_scan_valid`、`ps2_key_released` 给菜单控制器使用。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/src/game_console_top.v)) 但 slot2 里面又实例化了自己的 `console_ps2_rx`，slot3 也有自己的 `console_ps2_rx`。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/src/games/slot2/slot2_input.v))

这会带来三个问题：

第一，**资源重复**。PS/2 同步、滤波、位计数、奇偶校验、break code 解析等逻辑被多个游戏各自实现，没必要。

第二，**输入行为可能不一致**。同一组物理 `PS2_CLK/PS2_DATA` 被多个模块同时采样，不同 slot 的 reset/selected 状态不同，可能导致某个 slot 切入时处在不同的 PS/2 字节边界或释放码状态。

第三，**调试复杂度上升**。如果键盘某个键在菜单正常，在 slot2/slot3 表现异常，你很难一眼判断是游戏输入映射问题，还是 PS/2 接收器状态问题。

最后一轮如果时间够，我建议做这个架构优化：

```text
PS2_CLK / PS2_DATA
        ↓
top 中唯一 console_ps2_rx
        ↓
统一 key_event 总线：
    scan_code
    scan_valid
    key_released
        ↓
menu / slot1 / slot2 / slot3 / slot4
```

slot 内部只做“按键语义映射”，不要再各自接物理 PS/2 引脚。这个优化对资源、稳定性、代码可维护性都有价值，也非常适合在验收中讲成“输入系统架构优化”。

另外，Nexys A7 手册说明 PS/2 时钟和数据线是 open-drain/high-impedance 行为，使用时需要在 FPGA 内启用 pull-up；你可以检查 XDC 里是否对 `PS2_CLK`、`PS2_DATA` 加了 `PULLUP true`，如果没有，建议补上并上板确认。

```tcl
set_property PULLUP true [get_ports PS2_CLK]
set_property PULLUP true [get_ports PS2_DATA]
```

## 五、slot3 是最后一轮最值得优化的时序热点

`slot3_map.v` 是我认为最值得重点看的模块。它里面有一个 300 项的 `tile_map[0:299]`，并且带有 `(* ram_style="distributed" *)`。更关键的是，在 reset 和 `gen_start` 时，它用 `for (i = 0; i < 300; i = i + 1)` 一口气清空或生成整张地图；生成时还在循环里做 `i % 20`、`i / 20`，再调用 `template_tile(...)`。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/src/games/slot3/slot3_map.v))

这类写法在功能上很好理解，但在 FPGA 综合后通常会变成非常大的并行组合/寄存器写入网络。它的问题是：

```text
一拍内处理 300 个 tile
+ 循环中含除法/取模语义
+ template_tile 分支判断
+ tile_map 大量写端
= 高扇出、高组合深度、布线压力
```

这正是容易造成 WNS 紧张的典型结构。

建议改成 FSM 分周期生成地图：

```verilog
// 思路示意，不是直接替换代码
case (gen_state)
    IDLE: begin
        if (gen_start) begin
            addr <= 0;
            x <= 0;
            y <= 0;
            gen_state <= GEN;
            gen_done <= 0;
        end
    end

    GEN: begin
        tile_map[addr] <= template_tile_by_xy(x, y, template_id);

        if (addr == 299) begin
            gen_done <= 1;
            gen_state <= IDLE;
        end else begin
            addr <= addr + 1;
            if (x == 19) begin
                x <= 0;
                y <= y + 1;
            end else begin
                x <= x + 1;
            end
        end
    end
endcase
```

这样会把“300 个 tile 同拍生成”的大逻辑，拆成“每拍生成 1 个 tile”的小逻辑。地图生成多花 300 个 100MHz 周期，也就是 3 微秒左右，对游戏体验几乎没有影响，但对时序和布线会友好很多。

这应该是你最后一轮最值得做的优化之一。

## 六、渲染模块是 LUT 消耗和组合路径的主要来源

这个项目的 UI/显示逻辑比较重：菜单 renderer、slot2 renderer、slot3 renderer、tank 顶层渲染都包含大量坐标判断、字符判断、sprite 判断和颜色选择。当前结构是菜单 RGB 在总顶层按 `console_pixel_tick` 采样，游戏槽位 RGB 在各自 slot 边界按 `pixel_tick` 寄存，顶层只负责选择已稳定的 RGB。

这类设计在课程项目里完全合理，但最后一轮优化要注意两件事：

第一，**不要在像素组合路径里做除法、取模、复杂文本判断**。例如 slot3 文本/显示模块里如果存在 `col / 6`、`col % 6` 这类字符定位写法，综合后可能很不划算。能改成 8 像素宽字符最好，因为 `/8`、`%8` 可以变成位切片；如果必须 6 像素宽，也建议用小范围查表或计数器预计算。

第二，**把游戏状态计算和显示计算分开**。比如弹药、分数、生命、等级这些数值，不要在每个像素点实时算十位/个位，而是在游戏 tick 或 frame tick 时预先算好：

```verilog
always @(posedge clk) begin
    if (reset) begin
        ammo_tens <= 0;
        ammo_ones <= 0;
    end else if (logic_tick) begin
        ammo_tens <= dec_tens6(ammo);
        ammo_ones <= dec_ones6(ammo);
    end
end
```

`dec_tens6/dec_ones6` 用查表或有限范围 case 实现。这样 renderer 每个像素只负责查已经准备好的字符，不再承担算术逻辑。

## 七、slot2 的主要风险在 ghost / collision / renderer

slot2 已经拆成了 `tick_gen`、`input`、`game_core`、`renderer`，模块化比 tank 单文件好很多。`game_slot2_top.v` 里也能看到它是按输入、tick、core、renderer、七段数码管、蜂鸣器分层组织的。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/src/games/slot2/game_slot2_top.v))

但从优化日志和仓库的 tight setup pins 看，slot2 之前的关键路径与 `ghost_y_reg` 一类逻辑有关，说明“幽灵方块位置 + collision 判断 + 当前方块状态”仍然是敏感区域。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/tight_setup_hold_pins.txt))

建议：

```text
1. ghost 位置不要在一个周期内组合算到底；
2. collision 结果尽量提前一拍缓存；
3. 当前方块、ghost 方块、next 方块的 4x4 mask 预先算好；
4. renderer 不要每个像素重复调用复杂 piece_block_on；
5. side panel 文本尽量走统一 font/ROM。
```

slot2 现在最不该做的是继续往 renderer 里堆更多字符和判断。它应该朝“状态预计算 + 显示轻量化”的方向收尾。

## 八、slot1/tank 是典型历史包袱：功能完整，但单文件过大

slot1 通过 wrapper 接入 tank 游戏。tank 逻辑仍然属于“历史单体模块”：代码量大，游戏状态/显示/音效集中在一个文件里；但它已经不再自带 VGA/PS2 基础链路。当前 `tank_top` 复用顶层控制台生成的 VGA 像素坐标和 PS/2 byte 事件，避免了重复架构。

最后一轮如果没有时间大改，至少要做到：

```text
1. 确认 tank 输出 RGB 与 console 顶层 HS/VS 像素坐标严格对齐；
2. 确认切出 slot1 时所有 tank 状态被 reset 或冻结；
3. 确认 tank 内部 PS/2 与顶层 PS/2 不会产生不一致输入；
4. 如果报告里讲产品化，要说明 slot1 已从旧接口适配改为统一 console slot 接口。
```

这部分已按标准 `game_slot_api` 方向完成：显示使用顶层 `pixel_x/pixel_y/display_active/pixel_tick`，输入使用统一 PS/2 byte 事件，内部不再生成独立 VGA sync 或 PS/2 receiver。剩余可选优化是把单体 `tank_top.v` 进一步拆成多个 `tank_` 子模块。

## 九、构建脚本有一点“文档说法”和实际行为不完全一致

`scripts/build_bitstream.tcl` 的注释里说它是 incremental build script，但实际流程看起来是重新读取 Verilog/XDC、重新 `synth_design`，然后 `opt_design/place_design/phys_opt_design/route_design`，并没有真正读取已有 checkpoint 做 incremental implementation。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/scripts/build_bitstream.tcl))

这不是功能 bug，但属于交付质检问题。你有两个选择：

第一，简单做法：把注释改准确，不要说 incremental。

第二，进阶做法：真的实现 incremental：

```tcl
read_checkpoint -incremental path/to/previous_impl.dcp
place_design
route_design
```

对验收来说，我更建议你先选择第一种，保持脚本描述可信。老师如果问“你们怎么优化编译时间”，你可以说当前用了 Explore/AggressiveExplore、post-synthesis timing exception、post-route timing report 等脚本化流程，但不要夸大说已经实现了完整 incremental build。

## 十、XDC 方面：不要乱改 SW8/SW9 的 LVCMOS18

我特别提醒一个容易误判的问题：Nexys A7 的部分 switch 约束里，`SW8/SW9` 使用 `LVCMOS18` 并不一定是错，因为官方 Digilent Master XDC 里也是这样写的。([GitHub](https://github.com/Digilent/digilent-xdc/blob/master/Nexys-A7-100T-Master.xdc))

所以最后一轮 XDC 优化应该聚焦在：

```text
1. 端口名与顶层完全一致；
2. 未使用外设不约束；
3. PS2_CLK / PS2_DATA 检查 PULLUP；
4. create_clock 10ns 正确；
5. 没有 unconstrained path；
6. 没有把低有效七段数码管逻辑写反。
```

不要为了“统一 LVCMOS33”而把官方板级约束改错。

## 十一、最后一轮我建议你按这个顺序做

最稳妥的优化顺序是：

```text
第 1 步：修 slot2 duplicate named port。
第 2 步：检查并补 PS2 pullup。
第 3 步：干净跑一次综合，确认无语法/端口/约束 warning。
第 4 步：实现后跑 report_timing_summary + report_exceptions + report_unconstrained。
第 5 步：如果 WNS 仍低于 0.2ns，优先改 slot3_map 的 300 项同拍生成。
第 6 步：再处理 renderer 中的 /、%、重复字符判断、piece 判断。
第 7 步：有余力再统一 PS/2 receiver 到顶层。
第 8 步：更新 docs/structure.md 和优化日志，保证文档与当前代码一致。
```

我不建议你最后阶段大规模重构四个游戏，因为这会引入新 bug。优先级应该是：**修硬伤 > 稳时序 > 降低组合复杂度 > 清理脚本和文档 > 再谈资源美化。**

## 十二、验收前的严格交付标准

你最后交付前至少要满足这些条件：

```text
1. clean clone 后能从脚本创建/同步工程；
2. synthesis 无 duplicate port / missing module / critical warning；
3. implementation 成功；
4. WNS >= 0，TNS = 0，WHS/THS 不为负；
5. report_unconstrained 没有未约束路径；
6. timing exception 的对象数量非空且符合预期；
7. 四个 slot 都能从菜单进入、退出、reset；
8. PS/2 按下和释放都正常；
9. VGA 无明显闪烁、撕裂、错位；
10. 七段数码管低有效逻辑正常；
11. 蜂鸣器空闲为静音；
12. docs 里结构图、优化日志、构建说明与代码一致。
```

一句话总结：这个项目最后一轮优化的核心不是“再省一点点 LUT”，而是把当前“能跑的多游戏 FPGA 工程”打磨成“时序、输入、显示、脚本、文档都可信的课程产品”。最值得马上动手的是 **slot2 重复端口修复、timing exception 审计、slot3_map 分周期生成、PS/2 接收链路统一、renderer 算术和文本逻辑轻量化**。
