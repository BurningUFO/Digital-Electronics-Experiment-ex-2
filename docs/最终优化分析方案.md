## 现在最急的判断

当前项目结构是四个 slot 的 Nexys A7 游戏控制台，README 里也明确写了统一 VGA、`pixel_tick`、`display_active` 和 PS/2 byte 事件接口。([GitHub](https://github.com/BurningUFO/Digital-Electronics-Experiment-ex-2)) 结合当前代码和仓库里的 tight pin 文件，我现在会把 WNS 负数的急救优先级改成：

```text
第一优先级：slot2_game_core 的 ghost_y_reg / collision 路径
第二优先级：slot2_renderer 到 slot2 vga_r/g/b 寄存器的像素组合路径
第三优先级：确认 timing exception 是否真的被 Vivado run 吃到
第四优先级：slot3_renderer，仅在 report 明确指向 slot3 时再动
```

之前我提到的 `slot3_map` 一拍生成 300 tile，现在已经不用作为第一优化点了。当前 `slot3_map.v` 已经有 `generating/gen_tx/gen_ty`，每拍只写一个 `tile_map[...] <= template_tile(...)`，这个方向是对的。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/src/games/slot3/slot3_map.v))

## 1. 最急：slot2 的 `ghost_y_reg` 仍然是危险路径

仓库里的 `tight_setup_hold_pins.txt` 现在直接点名：

```text
u_game_slot2_top/u_core/ghost_y_reg_reg[2]/D
```

这基本说明历史最紧路径就是 slot2 核心里的 ghost 下落计算。([GitHub](https://github.com/BurningUFO/Digital-Electronics-Experiment-ex-2/raw/refs/heads/main/tight_setup_hold_pins.txt))

而当前 `slot2_game_core.v` 里，这个问题还没有真正拆掉：`ST_PLAYING` 状态下每个 100MHz 周期都会执行类似：

```verilog
if (!collision(cur_x, {1'b0, ghost_y_reg} + 7'd1, cur_rot, cur_type))
    ghost_y_reg <= ghost_y_reg + 6'd1;
```

同时同一个状态里还会做 gravity、soft drop、left/right、rotate wall kick 等多次 `collision()` 调用；`collision()` 本身又包含 4×4 方块扫描、`piece_shape()`、`board_row()`、边界判断和棋盘命中判断。([GitHub](https://raw.githubusercontent.com/BurningUFO/Digital-Electronics-Experiment-ex-2/refs/heads/main/src/games/slot2/slot2_game_core.v))

也就是说这条路径不是单纯的“小寄存器更新”，而是：

```text
ghost_y_reg / cur_x / cur_rot / cur_type / board_reg
  → piece_shape 大 case
  → 4×4 双层扫描
  → abs_x / abs_y 计算
  → board_row 20 选 1
  → hit 汇总
  → ghost_y_reg.D
```

这就是最应该先砍的路径。

### 立刻改法

不要再让 ghost 每个 100MHz 周期通过一个大组合 `collision()` 直接决定 `ghost_y_reg`。改成一个小 FSM：

```text
当 cur_x / cur_y / cur_rot / cur_type / board 发生变化：
    ghost_probe_y <= cur_y
    ghost_busy <= 1

ghost_busy 时：
    每拍只检查 ghost_probe_y + 1 是否碰撞
    不碰撞：ghost_probe_y <= ghost_probe_y + 1
    碰撞：ghost_y_reg <= ghost_probe_y，ghost_busy <= 0
```

这样 `ghost_y_reg` 的 D 端不再挂一整条大 collision 组合链，而是挂一个简单的寄存器赋值。俄罗斯方块 ghost 计算多花几十个 100MHz 周期，视觉上完全无感，但 WNS 会明显好很多。

## 2. 第二急：slot2 的 renderer 可能没有被 multicycle 覆盖

当前 `game_slot2_top.v` 已经修得比较规整了：slot2 不再自己接物理 PS/2，而是消费顶层传来的 `ps2_byte_ready/ps2_byte_data`；RGB 输出也在 `pixel_tick` 时注册到 `vga_r/g/b`。([GitHub](https://github.com/BurningUFO/Digital-Electronics-Experiment-ex-2/blob/main/src/games/slot2/game_slot2_top.v))

但问题是：你的 timing exception 脚本里覆盖了 slot3 RGB、slot3 video staging、tank VGA、console RGB sample、slot4 state/key 等路径，却没有明显覆盖 `u_game_slot2_top/vga_r_reg`、`u_game_slot2_top/vga_g_reg`、`u_game_slot2_top/vga_b_reg` 这类 endpoint。([GitHub](https://github.com/BurningUFO/Digital-Electronics-Experiment-ex-2/blob/main/scripts/apply_timing_exceptions.tcl))

而 `slot2_renderer.v` 本身不轻，它有棋盘格定位、`piece_block_on()`、ghost/current/next 方块判断、文本显示和数字显示等大量组合判断。([GitHub](https://github.com/BurningUFO/Digital-Electronics-Experiment-ex-2/blob/main/src/games/slot2/slot2_renderer.v)) 侧边栏还叠了很多 `text_on` / `digit_text_on` 级别的 UI 逻辑。([GitHub](https://github.com/BurningUFO/Digital-Electronics-Experiment-ex-2/blob/main/src/games/slot2/slot2_renderer.v))

所以如果你的 `timing_worst_50.rpt` 里 endpoint 是：

```text
u_game_slot2_top/vga_r_reg[*]/D
u_game_slot2_top/vga_g_reg[*]/D
u_game_slot2_top/vga_b_reg[*]/D
```

那当前最急就不是 ghost，而是 **slot2 renderer 的像素路径没有被 25MHz 像素节拍正确表达**。

### 这个不要粗暴乱加 multicycle

可以加 multicycle，但前提是路径来源真的只在 `pixel_tick` 节奏下变化，或者你先把来源寄存器也做 video staging。更稳的做法是像 slot3 那样，在 slot2 里增加一层 `*_video_q`：

```text
game state / board / piece / score
    → pixel_tick 时采样到 slot2_video_q
    → renderer 用 video_q
    → pixel_tick 时采样 RGB
```

然后再给 `slot2_video_q → slot2 vga_*_reg` 这类路径加 multicycle。否则如果 board 或 piece 状态在 100MHz 任意周期变化，你直接把它到 RGB 的路径标成 4-cycle，理论上有掩盖真实路径的风险。

## 3. slot3 现在不是首要问题，但 renderer 仍然重

slot3 现在做得比之前合理：`game_slot3_top.v` 里有大量 `*_video_q`，在 `pixel_tick` 时采样选中状态、游戏状态、玩家坐标、实体状态等，再把 renderer RGB 注册输出。([GitHub](https://github.com/BurningUFO/Digital-Electronics-Experiment-ex-2/blob/main/src/games/slot3/game_slot3_top.v))

但是 `slot3_renderer.v` 仍然是大组合模块，里面会遍历 smith、npc、bullet、bomb、pickup 等实体并判断像素命中。([GitHub](https://github.com/BurningUFO/Digital-Electronics-Experiment-ex-2/blob/main/src/games/slot3/slot3_renderer.v)) 如果 WNS report 指向 slot3 RGB，而 timing exception 的对象计数又正常，那才考虑继续拆 slot3 renderer；否则不要优先动它。

## 5. 最终急救建议

你现在不要再优先改 `slot3_map`，它已经优化过了。当前最值得马上动的是：

```text
1. 拆 slot2 ghost_y_reg 的每周期 collision 更新。
2. 减少 slot2_game_core 同一拍内并行调用 collision 的次数。
3. 如果最差路径指向 slot2 vga_r/g/b，给 slot2 renderer 增加 video staging。
4. 检查 timing exception 脚本是否真的挂到了当前 Vivado run。
```

一句话：**这次更新后，最可疑的 WNS 源头已经从 slot3_map 转移到 slot2：要么是 `ghost_y_reg + collision()`，要么是 slot2 renderer 的 RGB 采样路径。**
