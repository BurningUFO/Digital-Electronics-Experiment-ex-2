**你现在不是 FPGA 资源“不够”，而是实现风格太偏“像素级大组合逻辑”。**
 截图里顶层 `game_console_top` 用了 **30146 LUT / 63400，约 48%**，但寄存器只有 **4371 / 126800，约 3%**。Nexys A7-100T 本身有 **63,400 LUT、126,800 Flip-Flops、240 DSP、1,188Kb BRAM**，所以你现在最紧的是 LUT，不是寄存器、DSP 或 BRAM。

## 1. 资源占用分布说明了什么

你这个设计的资源特征很明显：

| 模块                      | LUT   | FF   | 现象                                               |
| ------------------------- | ----- | ---- | -------------------------------------------------- |
| `game_console_top` 总体   | 30146 | 4371 | LUT 接近一半，FF 很少                              |
| `u_console_menu_renderer` | 3327  | 5    | 典型纯组合文字/字体渲染                            |
| `u_console_vga_sync`      | 5829  | 108  | 数字异常偏大，可能是层级归属/flatten 影响          |
| `u_game_slot2_top`        | 6548  | 884  | Tetris 类游戏，核心状态 + 像素渲染组合逻辑         |
| `u_game_slot3_top`        | 8096  | 2530 | 最大热点，实体/地图/任务/文字/渲染逻辑都较重       |
| `u_game_slot4_top`        | 3483  | 142  | FF 极少，说明大量 tile/map/碰撞/像素判断是组合函数 |
| `u_tank_top`              | 3461  | 618  | 游戏逻辑中等，已改为复用集合机 VGA/PS2 公共接口   |

本轮结构优化后，`tank_top` 已删去内部 VGA/PS2 重复链路，slot2/slot3/slot4/tank 的 RGB 都在各自槽位边界按 `pixel_tick` 寄存。`src/` 下 Verilog 也已扫过真实 `/`、`%` 运算，当前未发现像素路径里的除法或取模残留。

这个分布的含义是：**你的 RTL 里很多“数据”和“选择逻辑”被综合成了 LUT 组合网络，而不是 ROM/RAM、寄存器流水线或可复用公共模块。** 截图左侧 `LUT as Memory` 只有约 1%，也说明文字、地图、字模、sprite、tile 等内容大概率没有被充分推成 ROM/RAM，而是被编译成大量 case / if / function / mux 树。

所以你后面优化的目标不应该是“单纯减少寄存器”，而是反过来：**适当增加寄存器和存储结构，把长组合逻辑切短，把 LUT 压力转移到 FF/BRAM/LUTRAM 上。**

## 2. 代码层面的问题在哪里

### 第一，全游戏模块现在是常驻综合，资源会线性叠加

你的 README 里要求 Vivado 工程添加 `src/` 下所有 `.v`，顶层是 `game_console_top`。 代码里 `game_console_top` 同时实例化了菜单、Tank、Slot1、Slot2、Slot3、Slot4，然后最后通过 active slot mux 选择输出。

这点非常关键：
 **`tank_selected`、`slot2_selected`、reset gating 只能让未选游戏运行时不动，不能让 Vivado 在综合时把它删掉。**
 只要模块被实例化，它的 LUT/FF 基本就会进入最终 bitstream。

所以你现在 30146 LUT 不是某一个游戏特别离谱，而是：

```
菜单 + Tank + Slot1 + Slot2 + Slot3 + Slot4 + 顶层 mux + 公共模块
```

全部加起来了。

这也是第一优先级优化方向：**综合时按需裁剪游戏，而不是运行时选择游戏。**

------

### 第二，菜单渲染器是典型的大组合文字渲染

`console_menu_renderer` 里有菜单标题、菜单项、help text、glyph 字模函数，以及大量基于 `pixel_x/pixel_y` 的组合判断。代码里 `title_char`、`item_char`、`help_char`、`glyph_row`、`glyph_pixel` 都是 case/function 形式，最后在 `always @(*)` 里直接决定当前像素颜色。

这解释了为什么：

```
u_console_menu_renderer = 3327 LUT, 5 FF
```

它几乎没有状态寄存器，但每个像素周期都要做：

```
坐标判断 -> 当前字符位置 -> 查字符 -> 查字模 -> 判断 glyph bit -> 颜色优先级
```

这些全是组合逻辑，自然吃 LUT。

菜单这种模块最适合改成：

```
text ROM -> font ROM -> 1~2 拍 pipeline -> RGB
```

而不是每个像素都展开一大堆 case。

------

### 第三，Slot2/Slot3/Slot4 的 renderer 都是 LUT 热点

`slot2_renderer` 里已经有 BCD 转换 FSM，这是一个比较好的“用时序换组合”的例子；但是它的 board 区域、piece shape、ghost piece、当前方块、文字显示，仍然大量依赖同一周期的组合坐标判断、动态 bit index、4x4 方块循环判断。

`slot3_renderer` 更典型。它在像素渲染路径里对 Smith、NPC、bullet、bomb、pickup 等对象做多组 for-loop 命中检测，再按图层优先级组合出 RGB。 这就是为什么 `slot3` 是最大热点：**它不是某个状态机特别大，而是“每个像素都并行判断一堆对象”。**

`slot4` 里也有明显问题：像素路径里用了 `pixel_x / CELL`、`pixel_y / CELL`，并且 tile 查询、碰撞查询函数多次调用。 如果 `CELL=20` 这类非 2 的幂，除法和取模即使 Vivado 会常数优化，也会变成不小的组合网络。这个方向很值得改。

------

### 第四，`u_console_vga_sync` 的 5829 LUT 要谨慎看

截图里 `u_console_vga_sync` 显示 **5829 LUT**，但我看源码后，这个模块本身主要就是 VGA timing 参数、`h_count/v_count`、`pix_div/pixel_tick`、`display_active`、`hsync/vsync` 这类常规计数器逻辑。

按正常经验，它不应该单独吃 5.8k LUT。这个数字更像是：

```
Vivado flatten hierarchy 后，把其他逻辑归到了这个层级下面
```

或者层级优化/跨层吸收导致的统计归属偏差。

所以不建议你第一刀去重写 VGA sync。你应该先用：

```
report_utilization -hierarchical -hierarchical_depth 6
```

并临时设置：

```
synth_design -flatten_hierarchy none
```

或者给关键模块加：

```
(* keep_hierarchy = "yes" *)
```

重新看一次层级资源。`keep_hierarchy` 只建议用于诊断，不一定适合最终优化版本。

------

### 第五，Tank 内部重复公共模块已移除

`game_console_top` 已经有一套 `console_vga_sync` 和 `console_ps2_rx`。本轮优化已经把 `tank_top` 改为消费总顶层提供的 `pixel_x/pixel_y/display_active/pixel_tick` 和 `ps2_byte_ready/ps2_byte_data`，不再实例化自己的 `vga_sync` 和 `ps2_rx`。

原问题会导致两个风险：

第一，资源重复；第二，架构不统一。
 更合理的结构应该是：

```
console 顶层统一提供：
pixel_x
pixel_y
display_active
frame_tick
pixel_tick
key_event / key_state

每个游戏只输出：
rgb
led
seg/an
buzzer
```

这样所有游戏共享 VGA timing、PS/2 解码、按键事件、七段扫描等公共基础服务。

Nexys A7 的七段数码管本来就需要动态扫描，`AN[7:0]` 和 `CA~CG/DP` 都是低有效；这类显示扫描也应该尽量做成顶层公共模块，而不是每个游戏各写一套。

## 3. 下一步优化方向，按优先级来

### 优先级 1：做“综合时裁剪”，先把不用的游戏不实例化

这是收益最大的方向。

你现在的问题不是单个 slot 必须优化到极致，而是所有 slot 同时存在。建议把 `game_console_top` 改成带参数的结构：

```
module game_console_top #(
    parameter ENABLE_TANK  = 1,
    parameter ENABLE_SLOT1 = 0,
    parameter ENABLE_SLOT2 = 1,
    parameter ENABLE_SLOT3 = 0,
    parameter ENABLE_SLOT4 = 0
)(
    ...
);
```

然后：

```
generate
if (ENABLE_SLOT3) begin : gen_slot3
    game_slot3_top u_game_slot3_top (...);
end else begin : gen_slot3_stub
    blank_game_slot #(.SLOT_ID(3'd3)) u_game_slot3_stub (...);
end
endgenerate
```

为什么这一步优先级最高？

因为只有 **generate / synthesis macro / 不实例化模块** 才能真正减少面积。
 `selected`、`reset`、`enable` 都是运行时信号，不能让 Vivado 在综合阶段删除整个游戏模块。

如果你只验收某一个游戏，可以先做：

```
MENU + 当前游戏 + blank stubs
```

这样 LUT 可能直接从 30k 降到几千到一万多，收益远大于抠某个 case 函数。

------

### 优先级 2：把文字、字模、地图、sprite 从组合 case 改成 ROM/RAM

重点改这些地方：

```
console_menu_renderer
slot3_text
slot3_renderer 中的 sprite / 图层素材
slot4_tile_raw / tile map
slot2 piece shape / 字符显示
```

菜单和文字模块尤其适合先改。现在 `console_menu_renderer` 是：

```
pixel_x/y -> 组合判断 -> char case -> glyph case -> RGB
```

建议改成：

```
stage 0: 锁存 pixel_x/y
stage 1: 计算 text_addr、glyph_row、glyph_col
stage 2: 读 text_rom 和 font_rom
stage 3: 输出 RGB
```

可以用这种风格：

```
(* rom_style = "distributed" *) reg [7:0] text_rom [0:TEXT_N-1];
(* rom_style = "block" *)       reg [7:0] font_rom [0:FONT_N-1];
```

小字体、小字符串可以用 distributed ROM；较大的 sprite、地图、图块表可以考虑 block ROM。Nexys A7-100T 有 BRAM 资源，但你截图里没有体现出 BRAM 被明显使用，所以这部分是很好的转移方向。

注意一点：**不要直接做完整 VGA framebuffer。**
 640×480×12bit 大约 3.7Mbit，超过板上 BRAM 规模。适合做的是 tile map、font ROM、sprite ROM、对象表，而不是整帧缓存。

------

### 优先级 3：给 VGA 像素渲染加 pipeline

你顶层代码里已经有注释提到：有些 renderer 是组合逻辑，`pixel_x/pixel_y` settle 时可能 glitch，所以在 visible pixel 上采样 RGB。 这说明你已经遇到了组合渲染路径的问题。

建议所有游戏 renderer 统一改成类似 3 到 4 级 pipeline：

```
stage 0:
  锁存 pixel_x, pixel_y, display_active

stage 1:
  计算 tile_x, tile_y, local_x, local_y
  计算是否在 board/map/ui 区域

stage 2:
  读 tile/font/sprite/object ROM
  计算对象命中

stage 3:
  做 layer priority
  输出 RGB
```

这会多用一些 FF，但你的 FF 只有 3% 使用率，完全值得。
 代价是 RGB 会延迟 1~3 个 pixel clock，所以 `hsync/vsync/display_active` 也要一起打拍延迟，保持和 RGB 对齐。

这个方向的收益主要有两个：

```
1. 缩短组合路径，提高时序稳定性；
2. 让 Vivado 更容易把 ROM/RAM、比较、mux 分阶段优化。
```

它不一定单独大幅降低 LUT，但和 ROM 化、裁剪一起做，效果会明显。

------

### 优先级 4：统一公共外设服务，不要每个游戏重复实现

建议顶层统一提供这些服务：

```
VGA timing
PS/2 receiver
keyboard event decoder
frame_tick / pixel_tick
七段数码管扫描
LED/buzzer 输出仲裁
```

然后每个游戏只接收抽象后的输入：

```
input  wire [9:0] pixel_x,
input  wire [9:0] pixel_y,
input  wire       display_active,
input  wire       frame_tick,
input  wire       pixel_tick,

input  wire       key_up,
input  wire       key_down,
input  wire       key_left,
input  wire       key_right,
input  wire       key_enter,
input  wire       key_space,

output wire [3:0] vga_r,
output wire [3:0] vga_g,
output wire [3:0] vga_b
```

Tank 这类旧模块要改成适配这个接口，不要内部再实例化 VGA 和 PS/2。这样资源更干净，后面 slot 的接口也统一。

当前代码已经按这个方向完成：slot1 wrapper 只做 API 适配，tank 本体只输出 RGB、LED、七段管和蜂鸣器。

------

### 优先级 5：消除像素路径里的除法、取模和重复函数调用

重点看 `slot4` 和 `slot2`。

`slot4` 中的：

```
cell_x = pixel_x / CELL;
cell_y = pixel_y / CELL;
```

如果 `CELL=20`，这不是简单移位，会综合成组合除法网络。

有三种改法：

第一，如果画面允许，把 `CELL` 改成 16 或 32。
 这样 `/ CELL` 和 `% CELL` 直接变成位切片，省很多 LUT。

第二，如果必须是 20，用计数器生成 `cell_x/cell_y/local_x/local_y`。
 因为 VGA 是顺序扫描的，不需要每个像素都重新除法。

第三，把碰撞检测从“像素路径组合查询”移出去。
 碰撞通常只在 frame tick 或 game tick 更新，不需要每个 VGA pixel 都算。

`slot2` 也类似。`board_idx = cell_y * 10 + cell_x`、4×4 piece loop、ghost/current piece 判断都可以拆成 pipeline，或者每帧/每 tick 预计算一部分结果。

## 4. 我建议你实际执行的顺序

第一步，先做准确基线，不要马上改代码：

```
report_utilization -hierarchical -hierarchical_depth 6 -file util_hier.rpt
report_timing_summary -file timing.rpt
```

然后临时关掉 flatten 再综合一次：

```
synth_design -top game_console_top -part xc7a100tcsg324-1 -flatten_hierarchy none
report_utilization -hierarchical -hierarchical_depth 6
```

重点确认 `u_console_vga_sync` 的 5829 LUT 到底是不是误归属。

第二步，做综合裁剪参数：

```
BUILD_TANK_ONLY
BUILD_SLOT2_ONLY
BUILD_SLOT3_ONLY
BUILD_SLOT4_ONLY
BUILD_FULL_CONSOLE
```

先分别得到每个 slot 的真实独立资源。这个会让你知道到底是哪个模块最值得优化。

第三步，先改 `console_menu_renderer`。
 它 3327 LUT / 5 FF，是最干净的优化样本。把它 ROM 化 + pipeline 化后，你会很直观看到 LUT/FF/时序的变化。

第四步，改 `slot3_renderer`。
 它是最大模块，实体命中检测和 layer priority 是主要目标。先把对象命中分 stage，再考虑 sprite/font/tile ROM。

第五步，改 `slot4` 的 `/ CELL`、`% CELL`、`tile_at_pixel` 和碰撞函数。
 这类组合函数反复调用很容易形成隐藏的大 mux/比较网络。

第六步，把 Tank 接入统一 console 接口，删掉内部 VGA/PS2 重复模块。

当前代码状态：第五步中的 `/ CELL`、`% CELL` 已清理，Tank 统一接口也已完成；后续若继续压 LUT，应优先看菜单/slot2/slot3 renderer 的 ROM 化和更细 pipeline。

## 5. 最核心的一句话

你现在的资源问题不是“寄存器用太多”，而是 **LUT 被像素级组合渲染、文字 case、地图函数、对象并行检测、全游戏常驻实例化吃掉了**。
